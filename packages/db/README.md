# @kpbooks/db

Postgres schema, Drizzle queries, and ledger-correctness migrations.

## Workflow

```bash
# 1. Start local Postgres
pnpm db:up

# 2. Generate the Drizzle schema migration (creates migrations/0000_*.sql)
pnpm --filter @kpbooks/db generate

# 3. Apply all migrations (Drizzle's 0000 + our hand-written 0001_init_rls.sql)
pnpm db:migrate

# 4. Open Drizzle Studio
pnpm db:studio
```

## What's hand-written vs generated

- `migrations/0000_*.sql` — generated by Drizzle from `src/schema/*.ts`. Don't edit by hand; regenerate.
- `migrations/0001_init_rls.sql` — **hand-written**. Defines the RLS policies, the `app.current_company` GUC plumbing, the deferred balance trigger, the closed-period guard, the locked-entry guard, and `updated_at` touchers. This is the file that makes the ledger trustworthy. Treat changes here like a constitutional amendment.
- Future hand-written migrations get the next number (`0002_*.sql`, etc.) and live alongside generated ones.

## Why deferred constraints

Posting a journal entry inserts the entry row + N line rows in one transaction. With an immediate constraint, intermediate states (e.g. one debit inserted before its credit) would fail. `DEFERRABLE INITIALLY DEFERRED` defers the balance check to `COMMIT`, so the whole entry is validated as an atom. That's the only honest model for double-entry.

## Why RLS

Multi-company isolation must survive a forgotten `WHERE company_id = ?` in app code. The RLS policy keys off `app_current_company()`, which the API plugin sets per request transaction. If the GUC isn't set, every read returns 0 rows and every write fails — fail-closed by design.
